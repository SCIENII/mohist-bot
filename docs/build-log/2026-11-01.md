# 2026-11-01 改造实录

一台 2012 年的笔记本，一台正在跑的旧服务器，一个晚上。

## 改造前的状态

机器叫 `mohist`：Ubuntu 22.04.5、i5-3230M（2C4T）、7.5G 内存、**零 swap**、无电池。
当时正在同时跑：一套自动回复业务（8 个容器）、一个游戏服务端、Samba、两条内网穿透（bore + SakuraFrp）。

已经存在的隐患：

- `ufw` 未启用，iptables INPUT 策略是 ACCEPT
- SSH 密码登录开着，口令是固定值，还配了 `NOPASSWD: ALL`
- 8 个容器**全部没有内存上限**
- fstab 里写的是 `/dev/sdb`，不是 UUID

## 时间线

### 01:21 停 Docker，开始迁移

决定了：Docker 的 `data-root` 和 containerd 镜像库都搬到新插的 128G SSD。

停服务时没有经验，直接 `systemctl stop docker docker.socket containerd`，没记 `docker stop -t`。
这一步后来导致的全套离线时间约 90 分钟。

### 01:24 第一次擦盘，失败

脚本按 `#>>>` 分块执行，每块是**独立的 shell**。
第一块里 `DEV=/dev/disk/by-id/...`，到第二块 `$DEV` 就是空的：

```
wipefs: no device specified
Error: Could not stat device mklabel - No such file or directory
```

盘没被擦（幸运），但接下来 `mkdir -p /mnt/ssd` 建在了**根盘**上，rsync 开始往根盘写。
两分钟内根盘从 13G 涨到 17G，剩 8.8G。

清理后恢复：27G 根盘，剩 14G。

**教训**：多步操作写成单个脚本文件整体执行，不要跨块依赖变量。

### 01:28 重新分区

```bash
wipefs -a $DEV
parted -s $DEV mklabel gpt
parted -s $DEV unit MiB mkpart swap      linux-swap 1    8193
parted -s $DEV unit MiB mkpart dockerext4 ext4       8193 100%
mkswap -L swapssd  ${DEV}-part1
mkfs.ext4 -L dockerssd -m 0 -F ${DEV}-part2
```

- swap 分区：8G
- 数据分区：108.9G，挂 `/mnt/ssd`

### 01:28 → 02:05 搬数据

| 内容 | 大小 | 耗时 |
|---|---|---|
| `/mnt/data/docker` | 5.9G | ~37 分钟 |
| `/mnt/data/containerd` | 14.8G | ~15 分钟 |

第一个慢、第二个快。差别在文件数：docker 目录是大量小文件（overlay、volumes），
containerd 是少量大 blob。机械盘的小文件随机读只有 ~2.7MB/s。

期间观察方式：`du -sm` 目标目录，配合 `/proc/<dockerd>/io` 判断是真在写还是卡死。

### 01:47 切换

```bash
ln -sfn /mnt/ssd/containerd /var/lib/containerd
# daemon.json: "data-root": "/mnt/ssd/docker"
# systemd drop-in: RequiresMountsFor=/mnt/ssd /mnt/data
systemctl daemon-reload && systemctl start docker
```

启动后 `docker info` 显示 `root=/mnt/ssd/docker driver=overlayfs`，
`docker images` 12 个镜像全在，8 个容器按 `unless-stopped` 自动回来了。

### 01:50 关掉旧服务

按需求把那套自动回复服务和游戏服务端全部停掉并 `--restart=no`。
内存从 1.4G 降到 731M。

### 01:57 Bot 容器起来

| 镜像 | 大小 |
|---|---|
| `soulter/astrbot` | 2.85G |
| `mlikiowa/napcat-docker` | 2.16G |

搬到 SSD 之后，5G 镜像的拉取+解压大约 15 分钟完成（之前在机械盘上 20 分钟只解了 5/8 层）。

### 02:04 → 02:16 自己把它搞掉线了

为了让 AstrBot 加载新写的 platform 配置，重启了两个容器。
`docker stop astrbot napcat` 默认 10 秒超时即 SIGKILL，QQ 客户端没来得及落盘会话。

结果：需要重新扫码。第一次以为是别的故障，排查了一圈才发现是重启方式的问题。

**之后统一改成 `docker stop -t 60`。**

### 02:16 写通道配置

AstrBot `cmd_config.json`：

```json
"platform": [{
  "id": "qq", "type": "aiocqhttp", "enable": true,
  "ws_reverse_host": "0.0.0.0", "ws_reverse_port": 6199
}]
```

NapCat `config/onebot11_<你的bot号>.json`：

```json
"websocketClients": [{
  "enable": true, "name": "astrbot",
  "url": "ws://astrbot:6199/ws", "messagePostFormat": "array"
}]
```

验证不再是看日志有没有报错，而是进网络命名空间看 socket：

```
ESTAB 172.20.0.2:6199 ← 172.20.0.3:55528
```

### 02:31 密码与重扫

AstrBot 首启打印的密码是错的（见踩坑清单第 4 条），用 CLI 重置：

```bash
printf '...\n...\n' | docker exec -i astrbot astrbot password
```

同时重启 NapCat 拿新二维码，这次用 `-t 60`。

## 复盘

**做对的**：
- 用 by-id 路径而不是 `/dev/sdc`，且每次破坏性操作前校验型号和容量
- 迁移前先备份 fstab 和 daemon.json
- 用 UUID 重写 fstab，顺手消灭了编号漂移的隐患
- 判断"是否可用"用可证伪的信号（数据库行数、socket 状态），不用"看着像好了"

**做错的**：
- 变量作用域 bug，导致第一次擦盘空跑，还污染了根盘
- 没有一开始就 `-t 60` 停 NapCat
- 迁移耗时估计过于乐观（估 45 分钟，实际 90 分钟），期间旧服务全断

**下次会怎么做**：
- 破坏性脚本一次写完、`set -euo pipefail`、进脚本前先 `lsblk` 打印一遍目标盘
- 迁移类操作先算文件数量，不只算体积
- 改容器配置前先问一句"这个容器重启会不会掉状态"
